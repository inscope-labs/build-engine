# build-engine — v0.5.1 Build Plan (Integration and Readiness Release)

Source: *Build Engine v0.5.1 — Android Replacement & Class B Gateway Readiness Assessment*.
Companion plan: `inscope-labs/operator-console` → `docs/V0.5.1-BUILD-PLAN.md`.
Baseline: `main` at v0.5.0 Basic (Class A-only, tag at `c95ae51`).
Status: **DRAFT for operator review.** Nothing here is approved until the operator closes the decisions in Stage BE-0.

This repository owns: the engine protocol and task model, the Class B read gateway
(`gateway/read/production/`), the Class B write gateway (`gateway/write/`), the conformance suite, the release
machinery, and the single cross-repository compatibility record. It does **not** own the Android app or the
operator gateway (Gateway A); those are in `operator-console`.

## 1. Principles

1. Integration, not rewrite. Land existing Phase 4/5 work; do not re-implement working components.
2. Three gateways, three trust boundaries, never collapsed (A = operator, B = Class B read, C = Class B write).
3. Three capability formats stay distinct: `ctxop-v1` (operator action), read-link signature (one file at a pinned
   commit), write root capability (one task's submission session). Each needs explicit cross-system conformance
   for signing, scope, expiry, revocation and replay.
4. Branch + PR per work package. Never push to `main`. Merge strictly in the stated order.
5. No claim without evidence: a gate passes only when its command ran and the output was inspected (RELEASE-PLAN G-06).
6. Fail closed (G-07). Credentials never appear in source, fixtures, URLs, workflow files or logs (G-08).
7. Gateway code, deployment secrets and conformance assets stay out of the consumer artifact (G-09); this is tested.
8. Operator publication authority is preserved (G-12). No agent or background process publishes, merges or widens access.
9. Do not publish any release claiming Termux replacement or Class B readiness until **Stage 6 of the assessment (BE-7 + OC-8) passes**.

## 4. Stages

Each stage lists intent, scope, acceptance and the evidence to record in `docs/release/PHASE-<stage>-REPORT.md`.

### BE-0 — Contract reconciliation and decisions (docs only)
- Intent: one authoritative contract for Gateways A/B/C, Android, engine and the three capability types (item 39).
- Scope: `docs/release/COMPATIBILITY-MATRIX.md` (supported combinations of engine, console APK, operator gateway, read
  gateway, write gateway); `docs/release/CAPABILITY-CONFORMANCE.md` (signing, scope, expiry, revocation, replay per
  capability); `docs/release/CBRIDGE-COVERAGE-MATRIX.md` (every `cbridge` command → native feature or documented
  alternative; items 27–29); task-state reconciliation (D-4); close D-1…D-7.
- Acceptance: decisions recorded in `docs/decisions/`; matrix reviewed by operator; version metadata plan agreed.
- Depends on: nothing. **Blocks everything else.**

### BE-1 — Land the Phase 4 read-gateway stack (items 11, 18 partial)
- Order: PR #7 `phase-4/conformance-foundation` → PR #8 `phase-4/production-read-gateway` → PR #11
  `phase-4/deployment-and-operations`. Rebase each onto current `main`; resolve conflicts without reverting Basic fixes
  (PENDING-REGISTER, changelog, STATUS, release verifier).
- Acceptance: each PR green on CI; shared harness (94 checks) and Worker conformance (58 cases) still pass after
  rebase; release isolation test proves `gateway/**` and conformance assets remain outside the artifact.
- Evidence: commands run and their outputs, per PR.

### BE-2 — Land the Phase 5 write-gateway stack (items 19, 20)
- Order: PR #13 (5.1) → #14 (5.2) → #15 (5.3) → #16 (5.4) → #22 (5.5). Merge each in order, not just #22.
- Acceptance: 362-test suite (247 unit / 85 integration / 12 load / 18 chaos) passes post-rebase; lifecycle verified:
  root capability, task/work-order binding, single writer, sequence/nonce, staging/file ops, UTF-8/file-type checks,
  quota, read-back/integrity, commit/delivery, seal/close/revoke.
- Constraint: Basic release improvements must not regress (diff review against `v0.5.0`).

### BE-3 — Workflow and deployment hardening (items 36, 37, 42)
- Remove every permissive CI expression (`|| true`) in gateway workflows; commit lockfiles; deterministic installs.
- Deployment becomes a protected, fail-closed sequence: typecheck → unit/integration → conformance → privacy and
  log-hygiene → bundle verification → staging acceptance → **explicit production approval** (GitHub environment with
  required reviewer).
- Acceptance: a deliberately failing gate demonstrably blocks deployment (record the run); release verifier still
  excludes gateway infrastructure, deployment secrets and conformance development assets.
- Note: workflow files are protected paths; they are authored by Claude/operator, not the AI Studio agent.

### BE-4 — Read gateway: real environments and deployment (items 12–18, 47)
- Provision test/staging/production Workers, **separate signing keys per environment**, read-only GitHub credential,
  repository and allowed-prefix configuration, production host/routing, revocation/audit state, operator admin credential.
  Secrets live only in Cloudflare/GitHub environment secrets.
- Execute the real staging then production deployment gates (local simulation is not evidence).
- Verify remote revocation and audit: after Worker restart, key rotation, unavailable state storage, provider failure.
- Run the shared conformance suite against the **deployed** gateway: unauthorized paths, expired links, bad signatures,
  replay, adjacent-file access.
- Link lifecycle contract for the console (item 16–17): select exact files → bind to immutable commit + work order →
  issue signed links; expiry, re-mint, revoke, status, audit retrieval. API shape lands in BE-0 and is consumed by OC-6.
- Acceptance: conformance run against staging archived; unavailable-state test fails closed.

### BE-5 — Write gateway: real environments and deployment (items 21–26, 47, 48)
- Create the dedicated submissions repository with pre-created submission branch and task-id folders (gateway never
  creates them and never receives access to the private consumer repository).
- Real Durable Objects + real GitHub provider responses: idempotency and recovery protocol, interrupted commit
  reconciliation without duplicate or divergent commits, rate limits, stale heads, Worker restarts, DO eviction.
- Log/metrics/trace/error privacy: no root URL, capability signature, payload, private content or credential
  (automated scan over captured staging logs).
- R0-005 / R0-007: implement or explicitly accept per D-5; GET-only protections (no-store, cache-control, non-prefetch,
  log hygiene) remain mandatory and tested.
- Acceptance: real delivery to a disposable submissions repo; sealing blocks further writes; revocation ends access.

### BE-6 — Submissions-to-consumer transfer (R0-011 for Standard; items 44, 45 gateway side)
- Supervisor-Agent transfer validates the sealed task folder, file hashes and expected destination SHA; **fails with no
  partial writes**. Credential boundary tested: submissions credentials cannot reach the consumer repository.
- Operator-side revocation and audit workflow exposed through the contracts consumed by OC-6.
- Acceptance: negative tests (tampered hash, moved destination head, unsealed folder, partial failure injection).

### BE-7 — Cross-system integration and Class B pilot (items 41, 49, 50)
- With `operator-console` OC-8: Android app against staging Gateways A, B and C using a disposable repository and a real
  Class B agent. Cover retrieval, submission, review, sealing, transfer, publication, revocation, audit inspection, plus
  the failure/recovery matrix from item 48.
- Acceptance: pilot evidence archived; all Severity 1 defects affecting advertised capabilities closed (item 50).
- **Retirement gate:** Termux CBridge is not declared retired unless OC-8 acceptance also passes.

### BE-8 — Release candidate, independent verification, publication (items 39, 42, 43)
- Update `VERSION`, `CHANGELOG`, `COMPATIBILITY.md`, `docs/STATUS.md`, shipped docs, `AGENT-WORKER-PROMPT.md`
  (gateway option reflects deployed state) per the D-1/D-2 outcome.
- Run `release/verify.sh --release`, self-tests, independent consumer install/update tests; produce the single
  compatibility record linking engine archive, APK, and the three gateway deployments (each independently versioned,
  with checksum).
- Publication requires explicit operator authorization at tag time (G-12). Changelog date set at tag time.

### BE-9 — Incidental, non-blocking (items 51, 53, 54, 52 partial)
- Gateway health/latency metrics, automated conformance score, and the evidence-derived **Operational Stability Index**
  (conformance, Android test results, availability, response times, submission success/failure, recovery results,
  security/authorization results). Not a subjective percentage; must not delay BE-8.

## 6. Gates and exit criteria

- Gate 0: D-1…D-7 closed in writing.
- Gate 1: Phase 4 and 5 stacks merged in order with passing CI and no Basic regression.
- Gate 2: deployed staging read and write gateways pass conformance; revocation/audit verified remotely.
- Gate 3: pilot and recovery evidence archived; Severity 1 count zero for advertised scope.
- Gate 4: release candidate verified independently; operator authorizes publication.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Stacked branch conflicts with Basic changes | Merge in order, rebase each, diff against `v0.5.0` |
| Local simulation mistaken for deployment proof | Gates require runs against deployed Workers |
| Version-label drift (0.5.1 vs 0.6.0) | D-1 decision recorded before any metadata change |
| Credential exposure | Secrets only in environment secrets; revoke and replace any token seen in chat |
| Contract divergence between repos | Single compatibility matrix + generated DTO validation (OC-0) |
