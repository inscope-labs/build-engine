# build-engine — v0.6.0 Standard Rollout Plan (single gated plan)

Proposed path: `docs/release/V0.6.0-ROLLOUT-PLAN.md`
Supersedes nothing: it executes `docs/release/V0.6.0-BUILD-PLAN.md` as one sequence of stage gates.
Status: **DRAFT for operator approval.** Nothing here is in force until the operator merges it.
Baseline: `main` at `d6587b7` (PR #48 merge, 2026-11-07). `VERSION` = `0.5.0`, tag `v0.5.0` at `c95ae51`,
protocol identifier `build-engine/0.6`.

## 1. What this plan is

One plan, ten stages (S0–S9). Every stage has an **entry gate** (what must be true before work starts) and an
**exit gate** (what must be true before the next stage may start). When S9 passes, `0.6.0` is published and
verified as a production-ready release (ADR 0006 decision 4 wording permitted).

The executing agent works **only inside `inscope-labs/build-engine`**. It never does the operator's work and
never does work in other repositories. What it does at every gate is **test the condition and record the
result**. A condition that depends on someone else (operator decision, production secret, console acceptance)
is not agent work. It is a gate condition the agent verifies, and if it is not met the agent stops.

## 2. Execution rules (apply to every stage)

1. **Branch + PR per work package. Never push to `main`.** The operator merges (G-12). Gates are tested against
   what is on `main` after the operator's merge, not against a branch, unless the gate says "on the PR".
2. **No claim without evidence (G-06).** A check passes only when its command ran and its output was inspected.
   Local simulation is never evidence for a deployment gate.
3. **Fail closed (G-07).** Any check that cannot run, errors, or returns ambiguous output is a FAIL.
4. **Credentials never appear in source, fixtures, URLs, workflow files, logs, reports or chat (G-08).** The
   agent verifies the *presence of secret names* (GitHub/Cloudflare APIs list names, never values). It never
   reads, prints, copies or stores a value.
5. **Three gateways, three trust boundaries, three capability formats stay distinct** (A operator, B read,
   C write; `ctxop-v1`, read-link signature, write root capability).
6. **Gateway code, deployment secrets and conformance assets never enter the consumer artifact (G-09).** Every
   stage that touches `release/`, `template/` or workflows re-runs the isolation checks (§4, check `C-ISO`).
7. **Protected paths.** Workflow files are authored by Claude/operator, no other AI build agent.
8. **Operator authority is preserved (G-12).** The agent never merges, approves a production deploy, widens
   access, tags or publishes without the operator's recorded authorization (S9 defines the record).
9. **Repository protection is part of every entry gate** (check `C-PROT`).

### Gate outcomes

| Outcome | Meaning | Agent action |
|---|---|---|
| **PASS** | Every check passed with inspected evidence | Write the stage report, open its PR, proceed after the operator merges it |
| **FAIL** | A repo-verifiable check failed | Fix within the stage's scope, re-run the **whole** gate, never partial credit |
| **BLOCKED-EXTERNAL** | A condition marked `[E]` or `[O]` is unmet | Stop. Report exactly which condition, which evidence was looked for, and where. Do not substitute, simulate or proceed |

### Condition types

- `[R]` repo-verifiable: a command, test, file or API query inside build-engine.
- `[E]` external input: supplied by the operator or another repository; the agent verifies presence and
  consistency only (secret *names*, environment exists, a cited commit exists, a cited report says PASS).
- `[O]` operator record: a written decision or authorization in a defined place (ADR on `main`, or the S9
  authorization comment). The agent verifies it exists, is by the repository owner, and says what the gate needs.

### Evidence and reports

Each stage ends with `docs/release/PHASE-<stage>-REPORT.md` (stage ids `S0`…`S9`) plus an agent report in
`agent-reports/`. Each check is recorded as: check id, command or query, exit code, the inspected output
excerpt, `main` SHA tested, UTC timestamp. A report states done / not done / blocked; nothing is implied.

## 4. Standing checks (referenced by every stage)

| ID | Check | Method |
|---|---|---|
| `C-PROT` | `main` requires a PR and the `test` check; force-push blocked | `GET /repos/inscope-labs/build-engine/branches/main/protection`; FAIL if weaker than the ADR 0009 record |
| `C-CI` | CI green on the tip of `main` | `GET /commits/main/check-runs`, all conclusions `success` |

| `C-CONF` | Shared conformance on the local runtime | `python3 conformance/harness/run.py all --reference` (94); `python3 -m unittest discover -s conformance -p 'test_*.py'` (14) |
| `C-READ` | Read gateway local checks | `npm test` (20), `npm run ops:check`, `npm run check:bundle`, `npm run check:staging:read` in `gateway/read/production` |
| `C-WRITE` | Write gateway local checks | `npm run typecheck`, `npm test` (372 at baseline; any change must be explained in the report), `npm run check:contract`, `npm run check:staging` in `gateway/write` |
| `C-ISO` | Release isolation | `release/package.sh dist` then `release/verify.sh dist/build-engine-v$(tr -d ' \n' < VERSION).tar.gz --test-payload`; the artifact contains no `gateway/**`, `conformance/**`, `ops/**`, `.github/**`, deployment config or secrets |
| `C-SECRETS` | No credential in the tree | pattern scan over the working tree and the PR diff (token prefixes, private-key headers, `Bearer` literals); FAIL on any hit |
| `C-DIFF` | Basic does not regress | `git diff v0.5.0..HEAD` reviewed for `template/`, `release/` allowlist/forbidden/manifest, `tests/`; each change listed and justified in the report |

Test counts are the baseline at `d6587b7`. If a count differs, the agent reports the difference and its cause
instead of adjusting the expected number silently.

## 7. What the agent does when blocked

Stop, write a short blocked report: stage, gate, condition id, what was checked, what was found, and what
evidence would clear it. Do not draft substitute decisions as if accepted, do not simulate a deployment, and do
not skip ahead. When the condition is cleared, re-run the whole gate for that stage from the top.
