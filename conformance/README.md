# conformance

The language-neutral acceptance suite for the signed-link scheme and the read gateway. It exists because the design says
"any implementation must reproduce" the signing vectors and a production port "must pass" eleven behaviours, but for a
long time those lived only inside Python tests. Anything that signs or serves links is accepted against this directory:
the shipped client (`template/engine/tools/ctxlink.py`), the reference gateway, and any production port in any language.

| File | Role | Status |
|---|---|---|
| `SCHEME.md` | the normative description of the scheme: message construction, signature, field rules, path rules, URL encoding, verification order, responses, audit record | written |
| `behaviours.md` | the eleven behaviours a gateway must pass (Appendix B of the design), each with a stable ID and the cases that cover it | written |
| `signing-vectors.json` | machine-readable signing vectors: 17 valid, 19 invalid | complete |
| `cases/behaviours.json` | the executable cases for B1 to B10, with the fixture they run against | complete |
| `harness/run.py` | the runner: drives a gateway over plain HTTP and a signer over a small JSON-lines contract | working |
| `harness/signer_adapter.py` | a worked example of the signer contract, over the shipped client | working |
| `test_conformance.py` | the acceptance gate for this repository: the client reproduces the vectors, the reference gateway passes the behaviours, and the suite has no holes | working |

## Running it

```bash
python3 conformance/harness/run.py all --reference      # the whole suite, against the reference gateway
python3 -m unittest discover -s conformance -p 'test_*.py'   # the same thing, as a test
```

CI runs the second form. Both are green on `main` at the time of writing.

## The published signing vector

The vector that has been published since the design was written: secret `test-secret`, key id `k1`, exp
`2000000000`, order `10008-S001`, ref forty `a` characters, path `amk/amk-ssot.md` gives signature
`b5aVA1G6MJDhZy5mkIkSFeUMFBM0W-tixIb2w4XHEU8`. The message is
`"ctxgate-v1\n" + kid + "\n" + exp + "\n" + order + "\n" + ref + "\n" + path` (UTF-8), HMAC-SHA256, base64url without
padding. It is in `signing-vectors.json` as `V01`, it is quoted in `template/docs/CONTEXT-EXPORT.md`, and it is asserted
in `template/engine/tools/test_ctxlink.py`; `test_conformance.py` fails if those three ever drift apart.

The second vector with a space and a non-ASCII character used to live only in the shipped test. It is now `V02` in
`signing-vectors.json`, and the shipped test keeps its own copy so that a consumer's installed copy can still be checked
without this directory.

## How the vectors were produced

They were computed by a second, independent implementation of the rules in `SCHEME.md`, cross-checked against the
OpenSSL CLI, and then compared with the shipped client. A vector file generated by the code it is meant to police would
prove nothing. `test_conformance.py` re-derives every vector from the spec, so the file cannot drift silently.

## Not shipped in releases

This is a development asset; a consumer never needs it. `release/manifest.txt` does not allowlist it, and
`test_conformance.py` asserts that it does not.

## What is still missing

The production port is not started. When it is, the port must pass this suite before it is deployed, and its signer must
be driven through `harness/signer_adapter.py`'s contract rather than by a bespoke test.
